# Как мы строим AI-среду

Принципы взяты из официальной документации Anthropic (ссылки в конце) и применены к Trava Motion.
Документ на утверждении (задача 0.6). После утверждения он фиксируется в ADR.

## 1. Главные принципы

| # | Принцип Anthropic | Что это значит для нас |
|---|---|---|
| P1 | **Начинать с простого, сложность добавлять только при необходимости.** «Find the simplest solution possible, and only increase complexity when needed» | Никаких агентов, skills и hooks «на будущее». Каждый механизм появляется, когда возникла конкретная потребность (см. раздел 3). |
| P2 | **Workflow, а не автономный агент, если задача хорошо определена.** | Наш pipeline — это цепочка шагов с проверками между ними (prompt chaining with gates). ✋-утверждения в бэклоге и есть эти gates. |
| P3 | **Дайте Claude способ проверить свою работу.** «Without a check it can run, "looks done" is the only signal available» | У каждой задачи есть проверка, которую можно выполнить: скрипт, сравнение скриншота с референсом, чеклист. Claude показывает доказательства (вывод команды, скриншот), а не просто пишет «готово». |
| P4 | **Explore → Plan → Implement → Commit.** | Каждую задачу бэклога начинаем с исследования и плана (plan mode). Код пишем только после утверждения плана. |
| P5 | **Контекст — главный ресурс.** Его заполнение ухудшает качество. | CLAUDE.md короткий. Справочные знания лежат в skills, которые загружаются по требованию. Одна сессия — одна задача. |
| P6 | **CLAUDE.md только для того, что нужно всегда.** Держать его меньше 200 строк, инструкции должны быть конкретными и проверяемыми. | Не описываем в нём структуру файлов и очевидные вещи. Для каждой строки спрашиваем: «станет ли Claude ошибаться без неё?» |
| P7 | **Skills пишутся по реальному опыту и проверяются оценками.** «Create evaluations BEFORE writing extensive documentation» | Skill появляется только после того, как этап пройден вручную и мы заметили, что повторяем одни и те же объяснения. Минимум 3 тестовых сценария, проверка свежей сессией Claude (Claude A пишет skill, Claude B его использует). |
| P8 | **Гарантии обеспечиваются hooks, а не инструкциями.** CLAUDE.md и skills — это просьба, hook — это принуждение. | То, что должно выполняться всегда (например, QA перед завершением), со временем переводим в hooks. |
| P9 | **Subagents нужны для изоляции контекста, а не для «ролей».** | Отдельный агент заводим, только если задача шумит в контексте или нужна независимая проверка («adversarial review»: свежий subagent проверяет diff по критериям). |
| P10 | **Прозрачность.** Шаги планирования видны явно. | План и решения лежат в репозитории (BACKLOG, ADR), а не в чатах. |

## 2. Наша концепция в терминах Claude Code

| Компонент из концепции | Механизм Claude Code | Где лежит | Когда появляется |
|---|---|---|---|
| Правила проекта | CLAUDE.md | `CLAUDE.md` | сейчас (фаза 0) |
| Правила для части репозитория (например, только для `animations/`) | path-scoped rules | `.claude/rules/*.md` с `paths:` | когда правил станет много |
| Skills (SVG Preparation, Motion Spec, GSAP, Responsive, Webflow, QA) | Skills | `.claude/skills/<name>/SKILL.md` | после ручного прохождения соответствующей фазы |
| Orchestrator | Skill-workflow, который запускается вручную (`disable-model-invocation: true`), работает в основной сессии | `.claude/skills/<name>/SKILL.md` | фаза 12 |
| Builder | Subagent, **только если** понадобится изоляция | `.claude/agents/<name>.md` | решение в фазе 12 |
| QA Reviewer | Сначала шаг orchestrator'а. Позже, возможно, subagent для независимой проверки или Stop hook | — | фаза 9 / 12 |
| Обязательные проверки | Hooks | `.claude/settings.json` | когда проверка уже существует и стабильна |
| Доступ к Figma | MCP (Figma) | настройки подключения | фаза 0.3 |
| Разрешения на команды | permissions allowlist | `.claude/settings.json` | когда появятся команды (фаза 4+) |
| Окружение облачной сессии | SessionStart hook (`npm install` и т.п.) | `.claude/settings.json` | фаза 4 |

Отличия от исходной схемы из брифа:
- Skills и агенты должны лежать в `.claude/skills/` и `.claude/agents/`, иначе Claude Code их не находит. Поэтому отдельных папок `skills/` и `agents/` в корне нет.
- Orchestrator — это не отдельный агент, а skill-workflow в основной сессии. Так он видит весь контекст задачи и останавливается на ✋ для утверждения.

## 3. Когда добавлять механизм (триггеры)

По рекомендации Anthropic «build your setup over time»:

| Триггер | Что добавляем |
|---|---|
| Claude дважды ошибся в соглашении или команде | строку в CLAUDE.md |
| Мы в третий раз объясняем одну и ту же процедуру | skill |
| Повторяем один и тот же стартовый промпт | skill, вызываемый вручную (`/name`) |
| Побочная задача забивает контекст | subagent |
| Действие должно происходить всегда, без исключений | hook |
| Копируем данные из Figma вручную | MCP |

## 4. Правила оформления (когда дойдём)

**CLAUDE.md**
- меньше 200 строк, разбит на заголовки и списки;
- конкретные проверяемые инструкции («запусти `npm run qa`», а не «проверь качество»);
- без описания структуры файлов и без того, что Claude может вывести из кода;
- `CLAUDE.local.md` для личных настроек, файл в `.gitignore`.

**Skills**
- `name`: строчные буквы, цифры и дефисы, до 64 символов, лучше в герундиальной форме (`preparing-svg`, `writing-motion-specs`);
- `description`: в третьем лице, что делает и когда использовать, до 1024 символов;
- тело SKILL.md меньше 500 строк, подробности в отдельных файлах, ссылки на них только на один уровень вглубь;
- рабочие процессы оформляются как чеклист, в котором есть цикл «проверить → исправить → повторить»;
- детерминированные операции выносятся в скрипты (выполнять, а не читать);
- единая терминология, без информации, привязанной к датам;
- до публикации: 3 тестовых сценария и проверка на реальной задаче.

**Subagents**
- узкая задача, понятное `description` (когда делегировать), минимальный набор `tools`.

## 5. Цикл работы над задачей бэклога

```
1. Explore   — Claude изучает вход (plan mode, без изменений)
2. Plan      — план + способ проверки → ✋ утверждение
3. Implement — маленькими шагами
4. Verify    — проверка из задачи; Claude показывает доказательства
5. Review    — для значимых изменений свежий subagent сверяет результат с планом
6. Commit    — коммит + отметка в BACKLOG; решения → ADR
7. Retro     — что повторялось? → кандидат в CLAUDE.md / skill (раздел 3)
```

Для фазы 1 (принципы движения) используем рекомендуемый Anthropic формат интервью: Claude задаёт
вопросы через AskUserQuestion, а итог записывается в spec-документ.
